## 2026-10-15: model timeout and checkpoint recovery

Run `9ed4825c0fbe47acafdd6a1cb5559c35` submitted the error-code, centralized exception
handling and logging requirement. Its implementation call hit the original
240-second deadline after planning and change approval. The run stopped safely,
but a stale node status made the graph appear to remain running.

The platform fix raises the default response limit to 15 minutes, exposes a
30-minute maximum, adds bounded checkpoint retry and elapsed activity reporting,
and terminates the owned CLI process tree on cancellation. The overall 30-minute
budget and model-call/repair caps remain in force. The original run was retried
through Chrome with its approved plan and consumed budgets retained. Validation
and live-run outcomes are distinguished in [timeout recovery evidence](../verification/TIMEOUT_RECOVERY.md).

The demonstration driver marks automatic decisions as `verification`. They prove
the approval gate, revision binding and promotion path work, but do not prove a
person authenticated and approved each change. Interactive decisions are recorded
separately as `workbench`; this local app does not assert verified human identity.

## Interview route

1. Read the five stage commits in order and the architecture diagram.
2. Start the app from the README; demonstrate the submitted service without a model.
3. Inspect recorded run evidence: requirements, parallel branches, source diffs,
   tests, repair attempts, decisions, requirement lineage and source revisions.
4. Discuss one failure and the evidence that distinguishes source repair from
   trusted runner repair. Show the obsolete approval being rejected.
5. Start a new live run only with the evaluator's own model access, then inspect
   and approve it interactively. Discuss the local-only and single-instance limits.
